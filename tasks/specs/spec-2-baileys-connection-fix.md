# Spec 2 — Baileys Connection Fix: QR Code & Build Reliability

## Overview

WhatsApp instance creation fails silently: Baileys connects to WhatsApp servers but is immediately
rejected with `<failure reason="405">` because the installed version (6.7.21) presents an outdated
protocol fingerprint. The instance loops in "connecting" state every 5 seconds indefinitely.

This spec covers four fixes that together restore QR code generation, prevent infinite reconnect
loops, make the build pipeline reliable, and add QR rendering via `qrcode` and `qrcode-terminal`.

## Root Cause (confirmed from logs)

```
"msg":"connected to WA"           ← WS handshake succeeds
"msg":"not logged in, attempting registration..."
"msg":"connection errored"        ← WS fails at noise protocol level
statusCode=405                    ← CB:failure reason="405" from WA servers
willReconnect=true                ← infinite reconnect loop
```

WhatsApp sent `<failure reason="405">` rejecting the outdated Baileys client fingerprint.

## Functional Requirements

### FR-1: Instance generates a QR code within 15 seconds of creation
After `POST /instances/create`, Baileys must successfully negotiate the WA Web protocol and emit a
QR code. `GET /instances/:name/qr` must return `{status: "qr", qr: "<string>", qrImageData: "data:image/png;base64,..."}`.

### FR-2: Dynamic WA version is fetched at socket creation time
Before `makeWASocket()`, call `fetchLatestBaileysVersion()` and pass the result as `version`.
Fall back to Baileys built-in default if the fetch fails.

### FR-3: QR is printed to terminal as ASCII art
When Baileys emits a QR code, `qrcode-terminal.generate()` prints it to stdout so developers can
scan it directly from the terminal.

### FR-4: QR endpoint returns a base64 PNG image
`GET /instances/:name/qr` returns a `qrImageData` field containing a data URL
(`data:image/png;base64,...`) generated by the `qrcode` library, enabling web UIs to render it.

### FR-5: Reconnect loop stops after 5 consecutive failures
After 5 failed reconnect attempts without `connection === 'open'`, the service stops, logs at
`error` level, and removes the instance from the registry.

### FR-6: `npm run build` exits 0 and produces `dist/`
Running `npm run build` always produces a `dist/` directory with compiled JS.

## Technical Requirements

### Change Surface

| File | Change |
|---|---|
| `package.json` | Pin Baileys to `7.0.0-rc.9`; add `qrcode ^1.5.4`, `qrcode-terminal ^0.12.0`; add `@types/qrcode`, `@types/qrcode-terminal` devDeps; build script uses `tsc -p tsconfig.build.json` directly |
| `tsconfig.build.json` | Add `"incremental": false` to override base config |
| `src/whatsapp/whatsapp.service.ts` | Import `fetchLatestBaileysVersion`, `qrcode-terminal`; add version fetch; add `retryCount`; circuit breaker in `handleConnectionClose`; terminal QR print on QR event |
| `src/whatsapp/interfaces/whatsapp.interface.ts` | Add `retryCount: number` to `Instance` |
| `src/instances/instances.controller.ts` | Import `qrcode`; return `qrImageData` in `/qr` endpoint |
| `nest-cli.json` | Add `"tsConfigPath": "tsconfig.build.json"` (informational — build uses tsc directly) |

### Data Model Addition

```typescript
export interface Instance {
  // ... existing fields ...
  retryCount: number;   // consecutive failed reconnects; resets to 0 on connection === 'open'
}
```

### API Contract Change (additive only)

`GET /instances/:name/qr` — adds `qrImageData` field and changes `status` from `"pending"` to `"qr"`:

```json
{
  "qr": "<baileys-qr-string>",
  "qrImageData": "data:image/png;base64,...",
  "status": "qr",
  "instance": "papagai01",
  "message": "🦜 Escaneie o QR code com seu WhatsApp"
}
```

## Constraints

- No new NestJS modules, controllers, or services.
- No REST API contract removals — only additive fields.
- `loggedOut` (status 401) must still result in immediate removal with no retries.
- `MAX_RETRIES = 5` must be a named static constant.
